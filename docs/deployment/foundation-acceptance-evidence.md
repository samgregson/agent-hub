# Foundation acceptance evidence

This is the evidence map for `docs/architecture/foundation-acceptance.md`. The continuous browser/API flow runs against the production web and API images, PostgreSQL, the fixture MCP backend image, and a local scripted OpenAI-compatible model. It follows one Project through two Threads without a live model credential or a hosted-platform dependency. A hosted walkthrough remains release validation.

| Item                                 | CI evidence                                                                                                                                                                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Project and two Threads           | The continuous flow creates a Project in the browser and two Threads through the browser-facing API.                                                                                                                            |
| 2. Persisted Deep Agent Runs         | Each Thread executes real Deep Agent Runs through the scripted model; Run status and history are read back from PostgreSQL-backed API routes. Checkpoint restore has a separate drill.                                          |
| 3. Streaming and approval UI         | The flow checks current-run AG-UI text and tool events, approves file and Artifact interrupts, then reloads the browser history and approval card. Error, rejection, and cancellation have targeted contract and browser tests. |
| 4. Shared Virtual Filesystem         | The first Thread writes an approved Project file; the second reads it through its own Agent Run. A host-path request is rejected, with deeper path cases in Module tests.                                                       |
| 5. Curated MCP tool and App          | The real fixture server answers an ordinary tool call through the gateway; its App renders the saved Artifact in the browser.                                                                                                   |
| 6. Portable Artifact operations      | The flow creates and semantically edits through the fixture gateway and renders the result. The fixture's standard MCP-client test validates the inline document.                                                               |
| 7. Saved Artifact and provenance     | The flow checks version 2 and creating/changing Thread provenance, then reopens the Artifact after a browser reload. The restore drill checks database recovery.                                                                |
| 8. Second Thread discovers and edits | The scripted model requests discovery, load, and Plugin-mediated edit in a real second-Thread Deep Agent Run; the fixture rejects unexpected tool availability.                                                                 |
| 9. First Thread notices change       | A later first-Thread Run receives the version-2 Project change notice; the scripted model fails if the notice is absent.                                                                                                        |
| 10. Standard MCP portability         | The ordinary FastMCP client test calls the same fixture version with an inline document and receives a complete replacement.                                                                                                    |
| 11. Explicit failure outcomes        | The flow checks a stale App edit returns 409. Targeted tests cover malformed results, Project authorization, interrupted Runs, unavailable Plugins, and request limits.                                                         |
| 12. Deterministic tests for seams    | The CI browser job runs the continuous flow, existing Playwright journeys, PostgreSQL drills, and whole-database restore. `make acceptance` adds contracts, lint, types, unit tests, and builds.                                |

The CI browser job starts from a fresh PostgreSQL service, builds and runs the production web/API/fixture images, and runs the continuous flow plus the existing browser tests. It also runs Run reconciliation, Artifact audit, and whole-database restore drills. The local acceptance target checks contracts, formatting, lint, types, unit tests, fixture client conformance, the Transform Runner image, and the production web build. Production operations use the hosting platform's health checks and container logs, plus PostgreSQL backups; they require no monitoring service.

The scripted model is bound only to loopback in CI. The fixture runs as a normal Python backend image. The hosting platform supplies sign-in and ingress in production; CI supplies a fixed test subject to the private API. Any later hosted walkthrough records deployment confidence without blocking #20.

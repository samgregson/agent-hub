# Foundation acceptance evidence

This is the evidence map for `docs/architecture/foundation-acceptance.md`. The contract requires one continuous CI flow against running production builds, PostgreSQL, and the separately runnable fixture MCP backend. Separate seam tests are useful evidence but do not close that gate. A hosted-platform walkthrough is release validation, not a foundation issue gate.

| Item                                 | Automated evidence                                                                                                    | Remaining CI flow check                                                                          |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 1. Project and two Threads           | Project API tests; restore drill seeds and restores two Threads                                                       | Create both through the running web app with a trusted test subject                              |
| 2. Persisted Deep Agent Runs         | Agent Run lifecycle tests; PostgreSQL reconciliation drill; LangGraph checkpoint restore                              | Run the real Deep Agent path with a scripted model in each Thread; reload and verify checkpoints |
| 3. Streaming and approval UI         | AG-UI contract tests; browser approval, rejection, and reload journeys                                                | Cover text, tool calls/results, errors, cancellation, and one approval in the continuous flow    |
| 4. Shared Virtual Filesystem         | Project Files module tests and path boundary tests                                                                    | Write in one Thread and read in the other; verify path confinement                               |
| 5. Curated MCP tool and App          | Portable fixture MCP client test; fixture App browser test                                                            | Call the running fixture backend through the API and render its App                              |
| 6. Portable Artifact operations      | Fixture MCP client create/validate/edit test and browser renderer test                                                | Create, validate, edit, and render through the running gateway                                   |
| 7. Saved Artifact and provenance     | Artifact Module tests; PostgreSQL restore drill verifies document, provenance, and audit record                       | Reopen the Artifact after page reload and verify Thread/Run provenance                           |
| 8. Second Thread discovers and edits | Deterministic two Thread Artifact flow test; Agent tool registration and approval policy tests                        | Discover and edit through a real Deep Agent Run using the scripted model                         |
| 9. First Thread notices change       | Project change notice middleware test; stale browser view and explicit reload test                                    | Observe the compact notice on a later Run and load the current Artifact                          |
| 10. Standard MCP portability         | Fixture's ordinary FastMCP client test accepts an inline document and returns a complete replacement                  | Run the same conformance test against the fixture version used in CI                             |
| 11. Explicit failure outcomes        | Stale edit, malformed MCP result, Project authorization, interrupted Run, unavailable Plugin, and request limit tests | Prove explicit outcomes at the running API boundary with controlled fault cases                  |
| 12. Deterministic tests for seams    | `make acceptance`, fixture client tests, PostgreSQL drills, and Playwright journeys                                   | Add one continuous browser/API journey spanning the preceding items                              |

The current CI browser job runs against a fresh PostgreSQL service. It also runs Run reconciliation, Artifact audit, and whole-database restore drills. The local acceptance target runs contracts, formatting, lint, type checks, unit tests, the fixture client test, the Transform Runner image test, and the production web build. The continuous CI flow above is still to be added. Production operations use the hosting platform's health checks and container logs, plus PostgreSQL backups; they require no monitoring service.

The CI flow needs the production web and API builds, PostgreSQL, and a separately runnable fixture MCP backend. It should start the fixture as a normal Python backend image and use a scripted model without a live model credential. The hosting platform supplies sign-in and ingress in production; CI supplies a trusted test subject to the private API. Any later hosted walkthrough records deployment confidence without blocking #20.
